======================================================================
0. STATUS, AUTHORITY, AND PURPOSE
======================================================================

This document is the consolidated implementation specification for the existing
Raaga AI Music Composer.

It combines and updates the previously discussed:
- Raga-aware interactive desktop composer requirements
- Self-learning Music Agent architecture
- Training/source-ingestion requirements
- Persistent Knowledge Base architecture
- Provider abstraction requirements
- UI changes discussed on 2026-09-03
- Current Apply Brief failure that must be fixed

For implementation, treat this document as the current canonical direction.
Do not throw away working code merely because a new architecture is described.
Inspect the existing repository first, map the requirements onto what already
exists, and extend/migrate rather than creating unnecessary parallel systems.

The immediate product is AUDIO.
Video/movie generation is future scope and must not delay the audio product.

The product is a Windows desktop application written primarily in Python.
It is not a browser application and not a generic prompt-to-song generator.

======================================================================
1. GOVERNING DEVELOPMENT PRINCIPLE
======================================================================

The development order is mandatory:

    COMPLETE -> WORKING -> RELIABLE -> CORRECT -> EXCELLENT

Definitions:

COMPLETE
Every required subsystem exists in at least a minimal form and is connected
end-to-end.

WORKING
Each required feature performs its intended basic function.

RELIABLE
The system works repeatedly without random failure, state loss, corruption,
silent failure, or inconsistent restart behavior.

CORRECT
Musical logic, raga behavior, command interpretation, timing, knowledge,
evaluation, and recommendations are technically and musically correct.

EXCELLENT
The system becomes musically compelling, expressive, original, fast, polished,
human-like, and production quality.

Do not reverse this order.
Do not over-polish one subsystem while required parts remain absent.

======================================================================
2. CORE PRODUCT VISION
======================================================================

Build an INTERACTIVE AI MUSIC-DIRECTOR WORKSTATION.

Do NOT build:

    PROMPT -> RANDOM FINISHED SONG

Build:

    CREATIVE DIRECTION
        -> RAGA
        -> TUNE
        -> APPROVAL / LOCK
        -> LYRICS FIT TO THE TUNE
        -> VOICE
        -> STUDIO VOCAL-ONLY MASTER
        -> INSTRUMENTATION / ARRANGEMENT
        -> MIX
        -> MASTER
        -> EXPORT

The creator remains in control.

The AI may:
- suggest
- reason
- compose
- generate alternatives
- infer instrumentation
- learn
- practice
- critique
- explain
- recommend

The creator may:
- accept
- reject
- override
- lock
- correct
- interrupt
- redirect
- ask why
- request alternatives

======================================================================
8. TUNE-FIRST WORKFLOW
======================================================================

The first major musical artifact is the TUNE.

Do not write final lyrics first.

Generate melody based on:
- selected raga
- creative brief
- mood
- feel
- song structure
- intended voice
- tempo/rhythm
- requested section

The creator must be able to:
- play
- pause
- replay
- accept
- reject
- regenerate
- create a variation
- modify one section
- change tempo
- change phrasing
- change emotional intensity
- preserve accepted sections

The approved tune must be lockable.

Generate Tune must NOT return a trivial single sustained note when meaningful
melodic generation is requested.

Minimum acceptable raga-aware tune behavior:
- multiple notes
- meaningful contour
- beginning, development, ending
- raga-valid note/phrase behavior
- characteristic phrases, not only scale traversal
- requested section respected
- requested length respected
- requested tempo respected
- requested mood/feel considered
- playable output produced

Progression by learning level may be:

Beginner:
- 2-4 note motifs
- tiny phrase variations

Intermediate:
- 1-2 bar phrases
- connected motifs
- simple cadences

Advanced:
- longer raga-valid development
- section-aware melodic architecture
- expressive variations

Excellent:
- original, memorable, emotionally coherent, technically faithful music

9. LYRICS

Central rule:

    TUNE FIRST -> LYRICS FIT THE TUNE

Lyrics should account for:
- syllable count
- note duration
- phrase duration
- stress
- breath points
- rhythmic placement
- language
- meaning
- emotional context
- raga phrasing where relevant

The creator must be able to edit or regenerate a line/verse/section without
destroying the locked tune.

======================================================================
11. ARRANGEMENT / INSTRUMENTATION
======================================================================

Only after the tune/vocal foundation exists should the creator and AI build the
arrangement.

The experience should resemble directing real musicians.

Examples:
- "Add veena here."
- "Use saxophone for this interlude."
- "Bring strings after this line."
- "Take the drums out here."
- "Use only piano for the first 15 seconds."
- "Add mridangam after the chorus."
- "Replace violin with veena."
- "Make this part lighter."
- "Give me another instrument that fits this feel."

Support:
- explicit instrument request
- feel-based instrument suggestion
- instrument replacement
- exact entry/exit timing
- region-only regeneration
- non-destructive changes

Any added instrument must work WITH the existing tune.

Consider:
- tonal center
- raga constraints
- melody contour
- phrase boundaries
- rhythm
- tempo
- existing instruments
- vocal register
- density
- frequency overlap
- section role

13.1 INTERRUPTION / BARGE-IN

The creator must be able to interrupt while:
- music is playing
- AI is explaining
- a preview is playing
- music is generating
- an arrangement is being auditioned

Newest explicit creator intent wins.

When redirected:
1. Capture command.
2. Determine affected job/region.
3. Cancel/pause/supersede obsolete work where safe.
4. Preserve unaffected accepted work.
5. Apply new instruction.
6. Resume as appropriate.

13.2 CONTEXTUAL REFERENCES

Resolve phrases such as:
- here
- there
- this part
- that instrument
- after that
- before the chorus
- from the second minute
- at the end
- do the same thing here
- keep everything else

Resolve against:
- current playback position
- selected timeline range
- last-mentioned track/instrument
- current song section
- recent conversation state

13.3 NATURAL LANGUAGE PLAYBACK

Support commands such as:
- Play the first minute.
- Play from the second minute to the third minute.
- Play the end.
- Play the last 30 seconds.
- Play from the chorus.
- Play this section again.
- Start five seconds before this point.
- Stop.
- Pause.
- Continue.
- Go back 10 seconds.

Transform the current static/semi-static composer into a persistent learning
music agent.

The system should behave like a musically talented student that:
- begins with foundational hearing skills
- follows an executable curriculum
- learns from approved sources
- analyzes audio/music
- extracts reusable knowledge
- stores durable knowledge
- practices
- gets evaluated
- retries weak areas
- learns one raga deeply before the next
- uses learned knowledge in composition
- learns from user critique
- continues from where it stopped after restart

The long-term objective is not merely "generate notes."
The objective is an exceptionally capable musical agent.

17. CURRICULUM ENGINE
======================================================================

The curriculum is executable system data, not merely documentation.

It determines:
- current learning goal
- prerequisites
- exercises
- required examples
- competency tests
- pass thresholds
- retry rules
- advancement rules
- revisiting earlier material

Curriculum progress must persist.

17.1 STAGE A - UNIVERSAL MUSICAL FOUNDATIONS

Teach:
1. Sound differentiation
2. Pitch discrimination
3. Stable tonic / Sa detection
4. Swara recognition
5. Sa Ri Ga Ma Pa Dha Ni Sa recognition
6. Swara variants where applicable
7. Ascending / descending movement
8. Interval recognition
9. Rhythm / pulse awareness
10. Short pattern recognition
11. Short pattern reproduction
12. Short pattern generation
13. Pattern transformation / variation

The system should hear a short sequence, represent it, compare it with another,
and create valid variations.

17.2 STAGE B - ONE RAGA AT A TIME

The preferred learning strategy is deep learning of one raga before moving to
the next major raga.

For each raga:
1. Raga identity
2. Arohanam
3. Avarohanam
4. Swara inventory
5. Important/resting swaras
6. Characteristic phrases / prayogas
7. Phrase boundaries
8. Phrase direction/contour
9. Gamaka behavior
10. Raga melodic grammar
11. Common mistakes / neighboring-raga drift
12. Very short raga-valid patterns
13. Short original phrases
14. Longer phrase chains
15. Geetham-level material
16. Swarajathi where appropriate
17. Varnam-level material
18. Kriti / Keerthanam understanding
19. Alapana development
20. Kalpana swara concepts
21. Longer-form original development
22. Expressive composition for mood/situation

Only advance after sufficient mastery.

17.3 STAGE C - CROSS-RAGA COMPARISON

After multiple ragas:
- distinguish similar ragas
- detect phrase ownership
- recognize ambiguous phrases
- understand shared notes but different grammar
- avoid accidental drift

22. CONTENT INGESTION / MUSIC ANALYSIS PIPELINE
======================================================================

For each user-approved source:

PHASE A - ACCESS CHECK
- verify source
- determine source type
- determine accessible representations
- transcript availability
- duplicate/already-learned detection
- provenance record

PHASE B - ACQUISITION
Use best permitted representation:
- transcript
- captions
- audio
- video
- local file
- article/text

PHASE C - PREPROCESSING
- normalize
- segment
- detect language
- identify speech vs music
- detect repeated material
- preserve timestamps
- preserve source references

PHASE D - AUDIO / MUSIC ANALYSIS

Initial minimum:
- audio decoding
- mono conversion where needed
- sample-rate normalization
- silence detection
- tonic/Sa estimation
- pitch contour extraction
- approximate swara mapping
- short-phrase segmentation
- timing information
- source metadata

Where appropriate, extract:
- pitch
- swaras
- phrase contours
- raga candidates
- arohanam
- avarohanam
- characteristic phrases
- prayogas
- gamakas
- tala
- tempo
- beat structure
- composition sections
- repetition
- cadence
- sangathis
- improvisation patterns
- voice exercises
- teaching explanations
- instrument references

Later improvements:
- gamaka contour representation
- phrase similarity
- ornament classification
- tala/beat alignment
- motif detection
- contour clustering
- singer/instrument separation where useful
- confidence scoring for noisy recordings

Do not require perfect transcription before learning anything.

PHASE E - SEMANTIC LEARNING
Determine:
- what is being taught
- what is new
- what confirms existing knowledge
- what contradicts existing knowledge
- what is uncertain
- what practical skill is demonstrated
- what examples matter
- what should be retained

PHASE F - VALIDATION
- internal consistency
- compare to KB
- duplicate detection
- conflict detection
- confidence
- alternative interpretation preservation
- never turn uncertain inference into fact

PHASE G - STORAGE
Store validated durable knowledge with provenance.

24. PRACTICE ENGINE
======================================================================

The agent must PRACTICE, not only consume information.

For every curriculum unit:
1. Learn examples.
2. Reproduce short patterns internally.
3. Generate variations.
4. Generate original patterns.
5. Evaluate.
6. Retry weak attempts.
7. Store scores.
8. Advance only when threshold is met.

Practice tasks may include:
- identify swara
- distinguish two swaras
- identify ascending vs descending phrase
- complete a phrase
- produce three variations
- classify valid vs invalid raga phrase
- generate 3-second motif
- generate 10-second phrase
- generate 30-second passage
- build a prelude
- build a pallavi
- improvise an alapana fragment

======================================================================
25. TRAINING AGENT / QUIZ BEHAVIOR
======================================================================

Add a Training Agent / Teacher role capable of testing the Musician/Music Agent.

Initial quizzes/exercises should include:
- swara recognition
- upper/lower register differentiation
- Sa-Ri-Ga-Ma-Pa-Dha-Ni-Sa identification
- ascending/descending recognition
- simple pattern recognition
- arohanam/avarohanam generation
- identify raga from a short clip/phrase
- distinguish among 3-4 learned ragas
- phrase validity
- progression from Geetham to Varnam to Keerthanam/Kriti to Alapana
- composition/variation tasks

Repeat weak tasks until mastery threshold is met.

When the agent reaches the defined readiness threshold, the system should be able
to notify/report that it is ready for the next level.

======================================================================
26. EVALUATOR / TEACHER / CRITIC
======================================================================

Score outputs on separate dimensions.

Do not collapse everything into one number.

Dimensions:
- swara correctness
- raga correctness
- phrase authenticity
- raga drift
- rhythm/timing
- melodic coherence
- originality
- mood match
- brief match
- structural quality
- musical interest
- expressiveness

Evaluator output:
- dimension scores
- detected mistakes
- confidence
- recommended correction
- pass/retry decision

User feedback has high weight.

Examples:
- "This does not sound like Keeravani."
- "Too mechanical."
- "I like the first 10 seconds."
- "Replace flute with violin."
- "Make this warmer."
- "Second phrase is good; keep it."

Attach feedback to the generated artifact and use it as learning evidence.

- analytical
- relational
- contextual
- evidence-aware
- cumulative
- searchable
- correctable
- self-improving

- open existing KB
- validate integrity
- load indexes/hot knowledge
- restore curriculum/queue/agent state
- continue

Normal shutdown:
- checkpoint writes
- persist state
- close cleanly

Crash recovery:
- recover committed data
- recover queue/state where possible
- never silently create a new empty KB

A new empty KB is allowed only for:
- first-ever run
- explicit user reset/new KB
- controlled migration
- isolated tests

34. CONFIDENCE / CONTRADICTION / VERSIONING
======================================================================

- 0.75-0.89 High
- 0.55-0.74 Moderate
- 0.30-0.54 Low
- 0.00-0.29 Unverified/speculative

Confidence may consider:
- source quality
- independent support
- direct demonstration
- agreement with trusted knowledge
- ambiguity
- extraction quality
- user confirmation
- contradiction level

Statuses may include:
- Candidate
- Learned
- Validated
- Accepted
- Disputed
- Superseded
- Rejected
- Deprecated
- Needs Review

Never silently overwrite conflicts.

Version changes instead of destroying old knowledge.
Record what changed, why, and what evidence/correction caused it.

======================================================================
35. DUPLICATE CONTROL / COMPACTION
======================================================================

Before adding knowledge:
- search canonical names
- aliases
- structured values
- semantic similarity
- source/evidence
- existing claims

Outcomes:
- exact duplicate -> attach new evidence
- near duplicate -> merge/link
- refinement -> new version / child claim
- genuinely new -> create item

Do not create hundreds of copies of the same fact.

Compaction may keep:
- one canonical rule
- multiple evidence records

Do not erase meaningful disagreement.

======================================================================
36. MEMORY / PERFORMANCE / SPEED
======================================================================

Speed is a design objective.

Use conceptual memory layers:

1. Persistent Knowledge
Durable source of truth.

2. Active / Working Knowledge
Small task-relevant context.

3. Cache
Frequently used pre-resolved/derived data for speed.

4. Raw Evidence Store
Transcripts, source segments, audio features, analysis artifacts.

Do NOT load the entire KB into every model prompt.

Use:
- exact lookup
- keyword lookup
- tags
- structured filters
- graph traversal
- semantic/vector search where useful
- confidence filters
- curriculum filters

Create a KnowledgeContextBuilder that retrieves the SMALLEST SUFFICIENT context.

Persist authoritative/non-recoverable knowledge, evidence, user feedback,
decisions, curriculum progress, and state.

Derived information that can be cheaply/reliably regenerated should not become
the authoritative source of truth merely because it was computed once.
Derived indexes/caches/embeddings may be rebuilt.
Audit-critical reports, provenance, accepted artifacts, and learning history
must still be retained where needed for traceability.

This balances learning depth with speed and storage efficiency.

- availability
